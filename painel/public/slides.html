Contexto

Por que um shade-matcher de bases?

  • O problema: cada marca numera os tons de base de um jeito diferente — o que é "NC30" na Boticário não é o mesmo tom em outra marca, e a pessoa compradora não tem como saber sem testar.
  • A ideia: o TomCerto é um "tradutor" de tom entre marcas, inspirado no Findation.com, adaptado para marcas e formatos vendidos no Brasil (líquida, cushion, mousse).
  • Por que POO aqui: este não é código descartável para a entrega — o modelo de domínio (Produto, subclasses, cálculo de compatibilidade) vira a base real do backend do produto depois do curso.

Pilar 1 de 4

Abstração

Produto é uma classe abstrata: não existe uma "base genérica" no catálogo, só líquida, cushion e mousse — cada subclasse é obrigada a implementar calcularCompatibilidade.

produto.py
class Produto(ABC):
    """Classe abstrata que representa
    um produto de maquiagem com tom."""

    # ... atributos encapsulados ...

    @abstractmethod
    def calcular_compatibilidade(
        self, perfil_desejado: PerfilDesejado
    ) -> float:
        """Cada subclasse implementa sua
        própria penalidade de acabamento."""
        raise NotImplementedError
Produto.java
public abstract class Produto {

    // ... atributos privados ...

    /**
     * Pilar: POLIMORFISMO na chamada,
     * ABSTRAÇÃO na definição do contrato.
     */
    public abstract double calcularCompatibilidade(
        PerfilDesejado perfilDesejado);

    protected double calcularScoreBase(
        PerfilDesejado perfilDesejado) { /* ... */ }
}
produto.ts
export abstract class Produto {
  // campos privados via # ...

  /**
   * Calcula compatibilidade (0-100).
   * Cada subclasse decide a penalidade.
   */
  abstract calcularCompatibilidade(
    perfilDesejado: PerfilDesejado
  ): number;

  protected calcularScoreBase(
    perfilDesejado: PerfilDesejado
  ): number { /* ... */ }
}

Encapsulamento

Atributos privados, acessados só por getter/setter — o setter de preço nunca deixa um valor negativo entrar no sistema, nas 3 linguagens.

produto.py
@property
def preco(self) -> float:
    return self._preco

@preco.setter
def preco(self, valor: float) -> None:
    if valor < 0:
        raise ValueError(
            "preco não pode ser negativo")
    self._preco = valor
Produto.java
private double preco;

public double getPreco() {
    return preco;

Pilar 3 de 4

Herança

BaseLiquida estende Produto: reaproveita marca, preço, subtom, acabamento e calcularScoreBase, e soma só o que é próprio dela — o FPS.

bases.py
class BaseLiquida(Produto):
    """Base líquida tradicional."""

    PESO_PENALIDADE_ACABAMENTO = 5

    def __init__(self, marca, nome, preco, tom,
                 subtom, acabamento, fps):
        super().__init__(
            marca, nome, preco, tom,
            subtom, acabamento)
        self.fps = fps  # passa pelo setter
BaseLiquida.java
public class BaseLiquida extends Produto {

    private static final double
        PESO_PENALIDADE_ACABAMENTO = 5.0;

    private int fps;

    public BaseLiquida(String marca, /* ... */
                        int fps) {
        super(marca, nome, preco, tom,
              subtom, acabamento);
        setFps(fps);
    }
}
bases.ts
export class BaseLiquida extends Produto {
  static readonly PESO_PENALIDADE_ACABAMENTO = 5;

  #fps: number = 0;

  constructor(marca, nome, preco, tom,
              subtom, acabamento, fps) {
    super(marca, nome, preco, tom,
          subtom, acabamento);
    this.fps = fps;
  }
}

Pilar 4 de 4

Polimorfismo

Um único laço percorre o catálogo pelo tipo Produto e chama calcularCompatibilidade — sem isinstance/instanceof. Cada objeto resolve com sua própria implementação.

main.py
for produto in produtos:
    # cada `produto` executa a
    # implementação da SUA classe,
    # sem isinstance/if-else
    compatibilidade = (
        produto.calcular_compatibilidade(
            perfil_desejado))
    resultados.append(
        (produto, compatibilidade))
Main.java
for (Produto produto : ranking) {
    // a JVM decide sozinha se quem
    // responde é BaseLiquida,
    // BaseCushion ou BaseMousse
    double percentual =
        produto.calcularCompatibilidade(
            perfilDesejado);
}
main.ts
for (const produto of catalogo) {
  // nenhum `instanceof` aqui
  const percentual =
    produto.calcularCompatibilidade(
      perfilDesejado);
  resultados.push({ produto, percentual });
}

Como funciona

Fórmula de compatibilidade

A distância entre o subtom do produto e o subtom desejado (escala 0–3: frio, neutro, oliva, quente) vira um score base de 0 a 100. Depois, se o acabamento não bate com o desejado, uma penalidade é descontada — e o peso dessa penalidade muda conforme a subclasse.

distancia = |subtom_produto - subtom_desejado| scoreBase = 100 * (1 - distancia / 3) se acabamento != acabamento_desejado: scoreFinal = max(0, scoreBase - penalidade) senão: scoreFinal = scoreBase
5BaseLiquida
10BaseMousse
15BaseCushion

Formatos mais rígidos (cushion) penalizam mais um acabamento incompatível; formatos mais versáteis (líquida) penalizam menos — refletindo como cada tecnologia se comporta na pele.
